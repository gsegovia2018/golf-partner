# Swing club detector on demand: a proposal on the frame the golfer chose

**Date:** 2026-10-16 · **Status:** plan, approved to build (owner, 2026-10-16: no new designs; reuse the proposed-dot visuals) · **Lifecycle:** `deliver` (no design step)
**Branch:** `feat/swing-club-on-demand` (worktree `.claude/worktrees/club-ondemand`), from `master` b284fb0e.
**Parent plans:** `2026-10-16-swing-club-detector.md` (the detector, apiVersion 4; §4 rules, §5 contract, §6.7 device findings) and `2026-10-11-swing-analyzer.md` D25–D28 (marking canvas: step 1 "Find the frame", step 2 "Place the marks", `ensureStills`, proxies), D31.

## 1. Goal

When the golfer chooses a frame other than the proposed one in step 1 of the marking canvas, the position opens step 2 with a **model clubhead proposal** on that frame instead of "Missing". The proposal looks and behaves exactly like a pass-2 one: a `proposed` dot, "Looks right · next", drag to move, Hidden. It is never confirmed by itself, never overwrites a clubhead the golfer placed or hid meanwhile, and a late answer for a frame no longer chosen is dropped. The label written to `marks.json` says the proposal came from the model on that frame (training data).

Non-goals: no change to pass 2's own proposals, no detection while scrubbing (only on the chosen frame), no proposal for the hands, no new copy or control, no iOS.

## 2. What exists today (read 2026-10-16)

- **Detector:** `ClubDetector.open(context)` (LiteRT 1.4.2, GPU delegate via `CompatibilityList`, CPU fallback; ≈ 0.5 s to open, ≈ 100 ms/frame GPU, ≈ 310 ms CPU on the Pixel 8 Pro) takes a 640 × 640 RGB byte array (`detect(rgb)` → boxes in 640 units). It is opened and closed **inside pass 2 only** (`Checkpoints.club()`), on the 13 checkpoint frames stretched from `YuvFrame.toRgb` (nearest neighbour). `ClubRules.dropStatic` votes over the checkpoint places (≥ 30 % = scenery), `head()` applies the 150 cm rule from the pose grip and picks a `head` box centre (`model`) or the far corner of a `shaft` box (`model-shaft`); `merge()` writes `shaft[frame] = { head, hidden: false, conf, source, boxes }`. **The stored `boxes` are the survivors of the static drop; the scenery boxes it removed are not stored anywhere.**
- **Canvas:** `SwingMarkCanvas` builds `{ draft, base }` once (`buildDraft`); `base.cps[key]` is the proposal at the proposed frame (`frame, hands, head, hidden, conf, source`). `takeFrame()` calls `chooseFrame(draft, base, key, view)`: on any frame other than `base.cps[key].frame` the head becomes `null` (Missing), hands `null`, nothing confirmed. The "Use frame N" button is **disabled until the picture is that exact still** (`loading`), and step 1 prefetches the cursor's ± 4 stills on the `neighbours` lane, so **by the time the golfer taps "Use frame N" its JPEG is always on disk** (`<swing>/frames/N.jpg`, display orientation, decoded size). `analyzeMarks` sends the head of a moved frame as a user mark, so `analyze()` (canvas `recompute` and Results) scores it from `marks.json` alone; `SwingOverlay` draws a `user` head as the white dot.
- **Native module:** one single-thread executor (`golf-swing`) for every async call; `cancelAnalysis()` cancels every job token (the stills queue calls it to supersede a stale neighbour prefetch). `extractFrames` is a sequential decode with seeks to the previous sync frame — a GOP of a 240 fps clip per target in the worst case.
- **Gates:** `API_VERSION = 4`; `REQUIRED_API_VERSION` 2, `PROXY_API_VERSION` 3, `CLUB_MODEL_API_VERSION` 4 in `native.js`.

## 3. Decisions

### 3.1 Native API: a separate `detectClub` on the still JPEG, not a field on `extractFrames`

**Why not `extractFrames`:** the frame the golfer chooses is on disk before the button is enabled (§2), so a detection riding on `extractFrames` would have to run speculatively on every `target` release in step 1 and would still miss the commonest case: a ‹ › nudge onto a prefetched neighbour (no native call at all). It would also share the video decoder's thread and queue (a neighbour prefetch of 8 frames runs ahead of it) and be cancelled by the stills queue's `cancelAnalysis()`.

**The decision:** `detectClub` reads the frame's **still JPEG** (`BitmapFactory.decodeFile` → `Bitmap.createScaledBitmap(640, 640, filter = true)` → RGB bytes) and runs the warm detector. No video decode, no seek: the cost is the JPEG decode (≈ 40 ms at 1080p) plus inference. The input differs from pass 2's (`YuvFrame` nearest-neighbour from YUV vs a q85 JPEG scaled bilinearly — closer to the lab's OpenCV path, if anything); the device round measures the gap (§5.1).

```
detectClub({ frames: [{ frame, still: 'file://…/frames/N.jpg', grip: [x, y] | null }],   // grip normalised (the smoothed grip at that frame)
             video: { width, height },        // display size: boxes and heads come back in this px space, like pass 2
             pxPerCm: number | null,          // analysis.scale.pxPerCm (150 cm rule)
             scenery: [{ cls, box: [x1, y1, x2, y2] }] })   // display px, pose.pass2.club.scenery (§3.2); [] = none
  -> { frames: { [frame]: { head: [x, y] | null, hidden: false, conf, source: 'model' | 'model-shaft' | null,
                           boxes: [{ cls, score, box }], error?: string } },
       timings: { openMs, inferMs, delegate: 'gpu' | 'cpu', warm: boolean } }
releaseClub()                                  // closes the warm detector now
```

`frames: []` is a legal call: it only warms the detector (§3.3). `API_VERSION = 5 // 5: detectClub / releaseClub, pass2.club.scenery (plan 2026-10-16 on demand)`. Additive: an apiVersion-4 binary has no `detectClub`, and the JS never calls it below the gate.

**Threading and lifetime.** A second executor, `golf-swing-club` (`newSingleThreadScheduledExecutor`), owns the detector so a neighbour prefetch never delays a proposal and the two never share a thread. `ClubWarm` (new, pure Kotlin, JVM-tested) holds the instance: `use { detector }` opens it on first use, reuses it afterwards, re-arms a 60 s idle close after every call, closes on `releaseClub()` and `OnDestroy`. All access is on that one thread (no locks). Pass 2 keeps opening its own instance on the main executor as today (the canvas is never open during pass 2; a Results re-analysis while the canvas is open on another swing would run two interpreters, slower but correct — noted, not handled). **Cancellation:** none; a call is ≤ 1 s and the JS drops stale answers. `detectClub` jobs have their own token set, so the stills queue's `cancelAnalysis()` never touches them. **Failure never fails the still:** nothing about the still changes; a bad JPEG or interpreter error leaves that frame's entry `{ head: null, source: null, error }`; an unavailable runtime (LinkageError, missing model) rejects once with `ERR_CLUB`, and the JS latches `unavailable` for the session and asks no more.

### 3.2 Scenery on one frame: store what pass 2 dropped; older swings run unfiltered

A single frame cannot vote. Pass 2 (apiVersion 5) **stores the boxes the static rule removed**: `ClubRules.splitStatic(dets, places)` returns `(kept, dropped)` (`dropStatic` = `.first`, existing tests unchanged); `ClubRules.scenery(dropped)` clusters them (same class, IoU ≥ 0.5 → one representative, the highest score; ≤ 20) and `Checkpoints.run()` writes them into the `club` block: `club: { model, input, conf, nms, scenery: [{ cls, score, box }] }` → stored as `pose.pass2.club.scenery` by `runAnalysis` as it is (`p2.club = r.club`). On demand, `ClubRules.dropScenery(boxes, scenery, minIou = 0.5)` drops any non-`hands` box matching a scenery box of the same class **before** `head()`.

**Swings analysed before (no `scenery` stored, i.e. `pose.pass2.club` has no `scenery`): the on-demand proposal runs with no scenery filter, explicitly.** The stored per-checkpoint `boxes` are post-drop and cannot identify scenery (the static boxes are exactly what is missing from them), and re-running the detector on the 13 stored stills to rebuild it would cost ≈ 1.5 s per canvas open for old swings only. The exposure is bounded: the 150 cm rule from the grip still applies, the chosen frame is usually a few frames from a checkpoint where the same scenery was already outvoted, and a wrong dot costs the same drag or Hidden as today's P6 false head (R4 of the parent). A golfer who wants the filter re-analyses (Results' "Analyse again" runs pass 2 on the new binary and stores `scenery`).

### 3.3 JS

- **Gate:** `native.js` `CLUB_ONDEMAND_API_VERSION = 5`, `clubOnDemandSupport()` beside `clubModelSupport()`, wrappers `detectClub(opts)` / `releaseClub()` (both throw `ERR_UPDATE_APP` below the gate, like `extractFrames`). `REQUIRED_API_VERSION` stays 2; an apiVersion-4 binary keeps everything it has today.
- **Seam:** `src/swing/clubOnDemand.js` (new): `proposeClub({ swingId, frame, grip, video, pxPerCm, scenery })` → `getStill(swingId, frame)` (null → resolves null, no call), `detectClub` with one frame → `{ head: [x / W, y / H], hidden: false, conf, source }` normalised, or null when `source` is null; the `unavailable` latch on `ERR_CLUB`; `warmClub()` = `detectClub({ frames: [] })` swallowed. Never rejects.
- **When it runs:** in `takeFrame()`, after `chooseFrame`, **when the new draft's head is null and not hidden** and either the chosen frame is not the proposal's, or the swing's pass 2 had no model at all (`!pose.pass2.club`: an apiVersion ≤ 3 analysis — same code path, so old swings get a proposal at the proposed frame too). Not when `base.cps[key].atFrame[frame]` already holds an answer (then `chooseFrame` used it, below). **Warm-up:** the first `pick()` to a frame other than the proposal in a canvas session calls `warmClub()` (≈ 0.5 s of GPU init that would otherwise land on the tap). `releaseClub()` on canvas unmount.
- **Model (`editMarks.js`):** `base.cps[key]` gains `atFrame: { [frame]: { head, hidden: false, conf, source } }` (proposals on other frames; empty from `buildDraft`). `proposalAt(base, key, frame)` = `frame === p.frame ? p : p.atFrame?.[frame] ?? null`. `headChanged`, `markStatus('head')`, `hasMarks`, `analyzeMarks` compare against `proposalAt(base, key, d.frame)` instead of `p` (so an untouched on-demand head is `proposed`, not `moved`; `hasMarks` still counts a non-proposal frame itself, so the "· marks reset" wording and the toast keep today's strings — `swing.mark.primary.useReset`, `swing.mark.framesReset`, no change). `chooseFrame` takes `head`/`hidden` from `proposalAt(base, key, frame)` when one exists (an answer that arrived early, or a frame chosen again), else `null`/`false` as today. New `applyProposal(draft, base, key, frame, proposal)` → `{ draft, base }`: always records `base.cps[key].atFrame[frame]`; sets `draft.cps[key].head` **only if** `draft.cps[key].frame === frame && head == null && !hidden && !confirmed.head` (a stale answer, a placed head, a Hidden tap or a confirmed mark win); `confirmed.head` stays false (`proposed`, not confirmed).
- **Canvas (`SwingEditMarksScreen.js`):** `base` becomes state (`useState(init.current.base)`; `live`, `statuses`, `action` already depend on it). The request's promise resolves into `applyProposal` through `latest.current` (current `draft`/`base`, never a closure); while a mark drag is in progress (`dragging`) the answer waits in a ref and is applied when `dragging` clears (D28: nothing re-renders the canvas mid-drag). Meanwhile the clubhead shows `missing` with today's line ("Tap the video where the clubhead is"); when the answer lands it becomes the `proposed` dot and "Looks right · next". No spinner, no new string.
- **Persisted (`labels.js` / `draftToMarks`):** the label's `head.proposed / proposedHidden / proposedConf / proposedSource` come from `proposalAt(base, key, d.frame)` — so a confirmed on-demand head stores `proposedSource: 'model' | 'model-shaft'`, `proposed` = the dot, `final` = where it ended — plus one optional field `head.proposedAt: frame` (the frame the proposal belongs to: `i` for an on-demand one, `iProposed` otherwise; absent in older files = `iProposed`). Schema stays `swing-club-labels/1` (compatible, like `confirmed` was). `buildDraft` reads a label's `proposedAt === label.i` back into `base.cps[key].atFrame[label.i]`, so reopening shows the same `proposed` status. No `pose.json` write: Results and the canvas both score the head from `marks.json` (`analyzeMarks` sends a moved frame's head as a mark), so a confirmed on-demand head reaches Results as `source: 'user'` and the white dot — identical to a head placed by hand on a moved frame today; the model source lives in the label.

## 4. Tests

- **Kotlin (`ClubDetectorTest` / new `ClubWarmTest`):** `splitStatic` returns exactly what `dropStatic` removes and keeps `dropStatic`'s existing cases green; `scenery()` clusters same-class boxes at IoU ≥ 0.5 into one representative (highest score), caps at 20, ignores `hands`; `dropScenery` drops a same-class match at 0.5, keeps a different class and `hands`, and the surviving `head()` picks the true head over a filtered spare club; `ClubWarm` with a fake opener and a fake scheduler: opens once across three uses, re-arms the idle close, closes on release and on idle, reopens after a close. The JPEG → RGB step is Android (`Bitmap`) and is covered on the device (§5).
- **JS:** `native.test.js` — apiVersion 5 → `clubOnDemandSupport()` true and `detectClub` forwarded; 4 → false and `detectClub` refused with `ERR_UPDATE_APP`. `clubOnDemand.test.js` — no still on disk → null, no call; px → normalised; `source: null` → null; `ERR_CLUB` latches and the next call never touches native. `editMarks.test.js` — `chooseFrame` onto a frame with an `atFrame` proposal gives a `proposed` head, unconfirmed; `applyProposal` ignores a stale frame but records it in `base`; never overwrites a placed, hidden or confirmed head; `markStatus` is `proposed` for an untouched on-demand head and `moved` after a drag; `hasMarks` is unchanged by an untouched proposal beyond the frame itself; `draftToMarks` writes `proposedSource: 'model'`, `proposedAt: i`, and `buildDraft` round-trips it. `SwingEditMarksScreen.test.js` — "Use frame N" on a supporting binary calls `detectClub` once with that frame's still and the grip, the dot appears as `proposed` when it resolves, a resolution after the golfer tapped Hidden changes nothing, and nothing is called on an apiVersion-4 mock.
