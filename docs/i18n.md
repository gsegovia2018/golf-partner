# Internationalisation (Spanish / English)

The app ships in Spanish (`es`) and English (`en`). The layer is plain JS in
`src/i18n/` on purpose: **no native module** (no `expo-localization`, no
`react-native-localize`), because any native change moves the runtime
fingerprint and stops OTA updates reaching installed APKs. Do not add one.

We wrote ~150 lines instead of using i18next: two languages, flat keys, `{param}`
interpolation and one plural rule fit in a file, and i18next + react-i18next add
roughly 40-50 kB minified to the web bundle for features we do not use.

## How it works

- Language = stored override (`'system' | 'es' | 'en'`, AsyncStorage key
  `@language_pref`, set in Settings > Display > Language) else the device
  language (`Intl.DateTimeFormat().resolvedOptions().locale`, then
  `navigator.languages`). Spanish if it starts with `es`, English otherwise.
- The override loads when `src/i18n` is first imported, so the pre-session
  marker page (`/m/:token`) and every other entry point get it with no wiring.

```js
import { useT, t, tr, formatNumber, formatDate, formatTime } from '../i18n';

const t = useT();                     // in a component: re-renders on language change
t('marker.confirm.title', { name });  // "Confirm Ana's card" / "Confirma la tarjeta de Ana"
```

| API | Use |
|-----|-----|
| `useT()` | In components. Returns `t(key, params)`; the component re-renders when the language changes. |
| `t(key, params)` | Outside components (module-level helpers, error messages). Not reactive: call it at render/event time, never cache the result in a module constant. |
| `tr({ key, params })` | Renders a message descriptor (see "Pure store modules"). |
| `formatNumber(n, { decimals, maxDecimals })` | `38.5` -> `38,5`; `1234` -> `1.234`. |
| `formatDate(d, style)` | `'short'` Sat 4 Oct / sáb 4 oct, `'day'`, `'long'`, `'month'`. Calendar strings (`2026-10-04`) never shift with time zone. |
| `formatTime(d, { timeZone })` | 24 h in Spanish (`18:30`), 12 h in English. Uses Intl for the zone, falls back to local time on runtimes without it (same trick as `leagueRules.cardMonth`). |
| `useLanguagePref()`, `setLanguagePref(v)` | The Settings row only. |

## Catalogues and keys

- Files: `src/i18n/locales/en.js` and `es.js` are index files that spread one
  module per area from `locales/en/` and `locales/es/` (`common`, `settings`,
  `profile`, `auth`, `onboarding`, `tour`, `marker`, `scorecard`, `leagueBoard`,
  `leagueCards`, `leagueMembers`, `leagueTimeline`, `leagueShare`, `courses`,
  `players`). Each area
  `profile`, `auth`, `onboarding`, `tour`, `marker`, `scorecard`, `shots`, `holeMap`,
  `leagueBoard`, `leagueCards`, `leagueMembers`, `leagueTimeline`, `leagueShare`). Each area
  `leagueCards`, `leagueMembers`, `leagueTimeline`, `leagueShare`, `feed`,
  `notifications`). Each area
  `leagueCards`, `leagueMembers`, `leagueTimeline`, `leagueShare`, `statsScreen`, `gameStats`, `statExplainers`, `statsTabs`, `myStats`, `playerStats`, `coach`). Each area
  `achievements` (round highlights), `leagueCards`, `leagueErrors`, `leagueJoin`, `leagueMembers`, `leagueMisc`, `leagueScoring`, `leagueTimeline`, `leagueShare`). Each area
  module is one flat object of dotted keys; the merged catalogue is still one flat
  object, so `t('league.board.x')` and imports of `locales/en` are unchanged.
  The same file name exists under both `en/` and `es/`.
  `en` is the source of truth and the fallback; a missing Spanish key shows
  English, a missing key everywhere shows the key (visible in review).
- Coach v2 keys live in `coach.js`: `stats.my.coach.cause.*` (likely causes), `stats.my.coach.swing.*` (swing link), `stats.my.coach.plan.*` (weekly plan), `stats.my.coach.ui.*` (Coach tab UI).
- Where a new string goes: in the area module for its screen group, in both
  `en/` and `es/`. A new area gets a new module (same name in both languages)
  plus an import, a spread and an `AREAS` entry in both index files. Never edit
  another batch's area file, which is what keeps parallel translation batches
  from conflicting. A key may live in only one module; a Jest test fails on a
  key in two modules or on `en`/`es` area sets that differ.
- Key shape: `area.screen.what`, camelCase segments, e.g. `marker.confirm.button`,
  `league.board.emptyTitle`. Use `common.*` for words shared by 3+ screens
  (`common.cancel`, `common.save`, `common.retry`). Do not build keys from
  user data; building them from a closed set is fine (`marker.${phase}.title`).
- Strings live in the catalogue, never inline in screens/components. Not
  translated: user-entered data (player, course, league names), tee names from
  the course data, brand name "Golf Partner", numeric units like `m`/`yds`
  only when the unit setting already controls them.
- Interpolation: `{name}`, `{count}`. Placeholders must be identical in both
  languages (a Jest test enforces it, and that key sets match). Never
  concatenate translated fragments, translate the whole sentence; when a
  sentence changes with data (name known or not) use two keys.
- Plurals: an entry that depends on a count is `{ one, other }` and `t` picks by
  `params.count` (`one` only for exactly 1, which is right for en and es):

  ```js
  'league.members': { one: '{count} member', other: '{count} members' },
  'league.members': { one: '{count} miembro', other: '{count} miembros' },
  t('league.members', { count: n })
  ```
- Numbers and dates shown to users always go through `formatNumber` /
  `formatDate` / `formatTime`, never `toFixed`, `toLocaleString` or hand-made
  month arrays. Pass already-formatted numbers as params
  (`t('x', { avg: formatNumber(avg, { decimals: 1 }) })`).
- Accessibility labels, placeholders, `Alert` titles and toasts are strings too.

## Pure store modules

`src/store/leagueView.js` and similar build user-facing text without React.
**Return message descriptors, not strings**: `{ key: 'league.status.playingNow', params }`.
The screen renders them with `tr(msg)` (or `t(msg.key, msg.params)`). Reasons:
store functions stay pure and deterministic in tests (assert on keys), nothing
is frozen in the language active when it ran (memoised or stored values stay
correct after a language switch), and the store never depends on React. Keep
computed parts (`lead`, counts, formatted numbers) in `params`.
When a module already returns `{ text, tone }`, replace `text` with
`msg: { key, params }` and update its tests. Do not import `t` into stores.

One exception: `src/store/leagueShare.js` builds the text a member shares to
the group chat. That text leaves the app, so it is finished text in the
sharer's language, built at the moment of sharing. Its builders take `lang`
and pass it to `t(key, params, lang)` and the format helpers explicitly, so
they stay pure and tests pin the language.

## Shared helpers that return finished text

Some helpers are used from many screens that are translated in different
batches, so they keep returning a string and call `t()` themselves, at the
moment they are called: `formatRoundLabel`, `computeSiIssues`,
`describeConditions`, `clubLabel` / `CLUB_CATALOG[].label` (a getter),
`historyModel` labels, `pointsText(points, unit)` / `unitText(unit)` in
`lib/pointsText.js` (units travel as the codes `'pts'` / `'holes'`, never as
words) and the errors thrown by stores. Call them at render or event time and
never cache the result in a constant. Their keys live in `locales/*/shared.js`
(`shared.*`); the round summary strip's statuses are descriptors in
`locales/*/scoring.js` (`scoring.summary.*`, rendered with `tr`).
Where a function must return plain text for many callers (member names, handicap
history lines) it lives in `src/lib/` (`leagueNames.js`) and calls `t` at render
time. Descriptor params may nest descriptors (`leagueStats`); render them depth-first. `tr()` does this for any param shaped `{ key, params }` (round achievements pass hole labels that way).
League server refusals: `LeagueError` keeps its English `message` and gains a
`descriptor`; show it with `leagueErrorText(err)` (`src/lib/leagueErrorText.js`), which
falls back to the server message. Hint-to-key map: `src/store/leagueErrors.js`.

Two render-time rules live in `t()` itself: in Spanish a `{month}`, `{otherMonth}` or
`{weekday}` param that starts a sentence is capitalised (`Octubre sigue ocupado.`), and
`teeDisplayName(label)` (`src/lib/teeName.js`) shows the seeded placeholder tee "Default"
as `shared.tees.defaultTee` while real tee names stay as written. The web `<html lang>`
follows the active language.

## Swing analyzer

The copy lives in `locales/*/swing.js` (screens), `swingChecks.js` (checkpoints, phases, check
labels, faults, measurement sentences), `swingCoach.js` (fix coaching), `swingCues.js` (marking
cues per checkpoint) and `swingDrills.js` (drills), keys `swing.<path>`. `src/swing/strings.js`
keeps the shape call sites read (`SWING_STRINGS.home.title`, `SWING_STRINGS.checkText.tempo(...)`):
a plain string is a getter that calls `t()` with the key of its own path when it is read,
a parameterised entry is a function that calls `t()` itself. Never cache a value in a module
constant. `checkpoints.js` (`cueFor`) and `drills.js` (`DRILLS`) work the same way; for a
left-hander `cueFor` mirrors `left/right` in English and `izquierdo/derecho` in Spanish.
`PROGRESSION` in `drills.js` is the English text kept for compatibility; screens read
`progression()`. Check `label` / `text` are written into `analysis.json` when the checks run
(on marking, club change), so a swing analysed in one language keeps its check sentences until
the checks run again. The default swing name (`defaultSwingName` in `swingStore`) is stored at
creation and is still English.

## Push notifications

Pushes arrive in the **recipient's** language (not the actor's), with the same
copy as the in-app inbox.

- **Where the language comes from.** `profiles.locale` (`'es' | 'en' | NULL`,
  migration `20261019000000_profile_locale.sql`). The app writes it through
  the RPC `set_my_locale(p_locale)` (SECURITY DEFINER, own row only, refuses
  anything but `es`/`en`, no-op when unchanged) from `src/lib/profileLocale.js`,
  started once in `App.js`. It sends `getLanguage()`, the effective language
  (the Settings override, else the device language, so `'system'` is never
  stored), debounced 1.5 s, when a session starts or signs in, on every
  language change and, after a failed send, when the connection comes back.
  Best-effort and silent: no UI, errors are swallowed and retried later.
  The push language is per account, not per device: with the app on two
  devices in different languages, the last device to start (or change
  language) wins, and every push to that account uses its language.
- **NULL means English.** NULL = the app has not reported yet (an older build,
  or not opened since the OTA). English is what every push said before this,
  it is the app's own fallback for an unknown device language
  (`resolveLanguage`), and nothing on the server knows better: a league has no
  language and the language preference lives only on the device. Most rows
  fill in on the first launch after the OTA.
- **Copy.** Deno cannot import the app, so `send-push` imports two plain JS
  modules from `supabase/functions/_shared/`:
  - `notificationCopy.js` is **generated**: every `notif.*` key of both
    catalogues plus the month names of `format.js`. Never edit it by hand.
    After changing a `notif.*` string in `locales/*/notifications.js` run
    `UPDATE_NOTIFICATION_COPY=1 npx jest notificationPush`.
  - `notificationRender.js` has `renderPushText(type, data, locale)`, which
    mirrors `renderNotification` in `src/lib/notificationContent.js` branch
    for branch.
  - `src/lib/__tests__/notificationPush.test.js` fails when the generated file
    is stale, when a type in `send-push`'s `DEEP_LINKS` has no copy in either
    language, and when push and inbox text differ for any type, payload variant
    or language. The one intended difference: the post deadline
    (`league_post_reminder`) is Madrid time in a push (a server has no zone) and
    device time in the inbox.
- **A new notification type** needs its copy in both `notifications.js`
  catalogues, a case in `renderNotification` and in `renderPushText`, a
  `DEEP_LINKS` entry and a `CATEGORY_BY_TYPE` entry in `send-push/index.ts`,
  then the regenerate command above.
- Rendering never fails the push: `renderPushTextSafe` retries in English if
  the recipient's language throws, and skips the push (logged) only if English
  throws too.
- The push payload (`to`, `title`, `body`, `sound`, `data` = the deep link) is
  unchanged; only the language of `title`/`body` follows the recipient.

## Tests for a translated screen

Existing English assertions keep working (tests run in English). Add one test
that sets `await setLanguagePref('es')` and checks a few strings, and reset it
in `afterEach` (see `MarkerCardScreen.test.js`).

## Spanish style (Spain)

Tú form, informal, short. Sentence case. No "Usted", no "Por favor" padding,
no Latin American vocabulary (`móvil`, not `celular`; `ordenador`; `vale`).
Imperative for buttons (`Confirmar tarjeta`, `Guardar`), infinitive is also
fine for short actions. Opening `¿ ¡` always. Keep "Golf Partner" untranslated.
