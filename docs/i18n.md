# Internationalisation (Spanish / English)

The app ships in Spanish (`es`) and English (`en`). The layer is plain JS in
`src/i18n/` on purpose: **no native module** (no `expo-localization`, no
`react-native-localize`), because any native change moves the runtime
fingerprint and stops OTA updates reaching installed APKs. Do not add one.

We wrote ~150 lines instead of using i18next: two languages, flat keys, `{param}`
interpolation and one plural rule fit in a file, and i18next + react-i18next add
roughly 40-50 kB minified to the web bundle for features we do not use.

## How it works

- Language = stored override (`'system' | 'es' | 'en'`, AsyncStorage key
  `@language_pref`, set in Settings > Display > Language) else the device
  language (`Intl.DateTimeFormat().resolvedOptions().locale`, then
  `navigator.languages`). Spanish if it starts with `es`, English otherwise.
- The override loads when `src/i18n` is first imported, so the pre-session
  marker page (`/m/:token`) and every other entry point get it with no wiring.

```js
import { useT, t, tr, formatNumber, formatDate, formatTime } from '../i18n';

const t = useT();                     // in a component: re-renders on language change
t('marker.confirm.title', { name });  // "Confirm Ana's card" / "Confirma la tarjeta de Ana"
```

| API | Use |
|-----|-----|
| `useT()` | In components. Returns `t(key, params)`; the component re-renders when the language changes. |
| `t(key, params)` | Outside components (module-level helpers, error messages). Not reactive: call it at render/event time, never cache the result in a module constant. |
| `tr({ key, params })` | Renders a message descriptor (see "Pure store modules"). |
| `formatNumber(n, { decimals, maxDecimals })` | `38.5` -> `38,5`; `1234` -> `1.234`. |
| `formatDate(d, style)` | `'short'` Sat 4 Oct / sáb 4 oct, `'day'`, `'long'`, `'month'`. Calendar strings (`2026-10-04`) never shift with time zone. |
| `formatTime(d, { timeZone })` | 24 h in Spanish (`18:30`), 12 h in English. Uses Intl for the zone, falls back to local time on runtimes without it (same trick as `leagueRules.cardMonth`). |
| `useLanguagePref()`, `setLanguagePref(v)` | The Settings row only. |

## Catalogues and keys

- Files: `src/i18n/locales/en.js` and `es.js` are index files that spread one
  module per area from `locales/en/` and `locales/es/` (`common`, `settings`,
  `profile`, `auth`, `onboarding`, `tour`, `marker`, `scorecard`, `leagueBoard`,
  `leagueCards`, `leagueMembers`, `leagueTimeline`, `leagueShare`, `courses`,
  `players`). Each area
  module is one flat object of dotted keys; the merged catalogue is still one flat
  object, so `t('league.board.x')` and imports of `locales/en` are unchanged.
  The same file name exists under both `en/` and `es/`.
  `en` is the source of truth and the fallback; a missing Spanish key shows
  English, a missing key everywhere shows the key (visible in review).
- Where a new string goes: in the area module for its screen group, in both
  `en/` and `es/`. A new area gets a new module (same name in both languages)
  plus an import, a spread and an `AREAS` entry in both index files. Never edit
  another batch's area file, which is what keeps parallel translation batches
  from conflicting. A key may live in only one module; a Jest test fails on a
  key in two modules or on `en`/`es` area sets that differ.
- Key shape: `area.screen.what`, camelCase segments, e.g. `marker.confirm.button`,
  `league.board.emptyTitle`. Use `common.*` for words shared by 3+ screens
  (`common.cancel`, `common.save`, `common.retry`). Do not build keys from
  user data; building them from a closed set is fine (`marker.${phase}.title`).
- Strings live in the catalogue, never inline in screens/components. Not
  translated: user-entered data (player, course, league names), tee names from
  the course data, brand name "Golf Partner", numeric units like `m`/`yds`
  only when the unit setting already controls them.
- Interpolation: `{name}`, `{count}`. Placeholders must be identical in both
  languages (a Jest test enforces it, and that key sets match). Never
  concatenate translated fragments, translate the whole sentence; when a
  sentence changes with data (name known or not) use two keys.
- Plurals: an entry that depends on a count is `{ one, other }` and `t` picks by
  `params.count` (`one` only for exactly 1, which is right for en and es):

  ```js
  'league.members': { one: '{count} member', other: '{count} members' },
  'league.members': { one: '{count} miembro', other: '{count} miembros' },
  t('league.members', { count: n })
  ```
- Numbers and dates shown to users always go through `formatNumber` /
  `formatDate` / `formatTime`, never `toFixed`, `toLocaleString` or hand-made
  month arrays. Pass already-formatted numbers as params
  (`t('x', { avg: formatNumber(avg, { decimals: 1 }) })`).
- Accessibility labels, placeholders, `Alert` titles and toasts are strings too.

## Pure store modules

`src/store/leagueView.js` and similar build user-facing text without React.
**Return message descriptors, not strings**: `{ key: 'league.status.playingNow', params }`.
The screen renders them with `tr(msg)` (or `t(msg.key, msg.params)`). Reasons:
store functions stay pure and deterministic in tests (assert on keys), nothing
is frozen in the language active when it ran (memoised or stored values stay
correct after a language switch), and the store never depends on React. Keep
computed parts (`lead`, counts, formatted numbers) in `params`.
When a module already returns `{ text, tone }`, replace `text` with
`msg: { key, params }` and update its tests. Do not import `t` into stores.

One exception: `src/store/leagueShare.js` builds the text a member shares to
the group chat. That text leaves the app, so it is finished text in the
sharer's language, built at the moment of sharing. Its builders take `lang`
and pass it to `t(key, params, lang)` and the format helpers explicitly, so
they stay pure and tests pin the language.

## Push notifications (not implemented yet)

`supabase/functions/send-push` and `src/lib/notificationContent.js` render copy
in English only. Proposal: add `locale text` (`'es' | 'en'`, nullable) to
`profiles`, written by the app from `getLanguage()` on sign-in, on every
language change and when the push token is registered. `RENDERERS` in
`send-push` then takes `(data, locale)` and a small `{ es, en }` copy table
(Deno cannot import app code, so the table is duplicated and a test should
compare its keys with `notificationContent.js`). Recipient's language, not the
actor's; unknown/null -> English. Needs a migration + edge function deploy, so
it is its own PR.

## Tests for a translated screen

Existing English assertions keep working (tests run in English). Add one test
that sets `await setLanguagePref('es')` and checks a few strings, and reset it
in `afterEach` (see `MarkerCardScreen.test.js`).

## Spanish style (Spain)

Tú form, informal, short. Sentence case. No "Usted", no "Por favor" padding,
no Latin American vocabulary (`móvil`, not `celular`; `ordenador`; `vale`).
Imperative for buttons (`Confirmar tarjeta`, `Guardar`), infinitive is also
fine for short actions. Opening `¿ ¡` always. Keep "Golf Partner" untranslated.
